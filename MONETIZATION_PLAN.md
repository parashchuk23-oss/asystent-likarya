# Monetization Plan

Документ описує можливу монетизацію проєкту «Асистент лікаря» без поточного впровадження оплати, авторизації або бази даних.

Головний принцип: монетизація не повинна ламати простоту продукту, змушувати лікаря передавати персональні дані пацієнтів або обмежувати доступ до базових медичних інструментів.

## 1. Поточні модулі сайту

На сайті вже присутні такі основні розділи:

* Головна.
* Асистент лікаря.
* Калькулятори.
* Опитувальники.
* УЗД.
* ЕКГ.
* Препарати.
* Хвороби.

### Головна

Коротко пояснює продукт, його користь і дає переходи до основних робочих розділів.

### Асистент лікаря

Структурована форма консультації з accordion-секціями:

* паспортна частина;
* скарги;
* об'єктивний статус;
* клінічні дані;
* заключення.

Заключення формується локально на основі введених даних і редагується лікарем.

### Калькулятори

Реалізовані клінічні інструменти:

* SCORE2 / SCORE2-OP;
* SCORE2-Diabetes;
* SMART Risk Score;
* CKD-EPI 2021;
* Cockcroft-Gault;
* ACR;
* KDIGO-ризик;
* оцінка маси тіла;
* оцінка антикоагулянтної терапії при фібриляції передсердь;
* HEART / біль у грудях;
* серцева недостатність зі збереженою ФВ (HFpEF);
* венозна тромбоемболія;
* оцінка ризику остеопоротичних переломів.

### Опитувальники

Реалізовані:

* GAD-7;
* PHQ-9;
* FINDRISC;
* AUDIT-C;
* Тест Фагерстрема на нікотинову залежність;
* STOP-Bang;
* Epworth.

Є друковані форми, результат, інтерпретація, а для GAD-7 / PHQ-9 — локальні рекомендації для пацієнта.

### УЗД

Реалізовані локальні конструктори протоколів:

* УЗД щитоподібної залози;
* УЗД органів черевної порожнини.

Формуються оглядова частина, висновок, рекомендації та текст для копіювання.

### ЕКГ

Реалізований MVP «ЕКГ-помічника»:

* чек-лист аналізу ЕКГ;
* QT / QTc;
* електрична вісь;
* підготовлені майбутні підрозділи: гіпертрофія, провідність, STEMI, VT / SVT, ЕКГ-синдроми.

### Препарати

Практичний довідник лікаря:

* БРА / сартани;
* ІАПФ;
* блокатори кальцієвих каналів;
* тіазидні та тіазидоподібні діуретики;
* бета-блокатори;
* «Доступні ліки» з локальним JSON-переліком і імпортером офіційного переліку НСЗУ.

### Хвороби

Клінічні шаблони для формування діагнозів, МКХ-10 підказок і рекомендацій.

Поточні картки:

* гіпертонічна хвороба;
* ІХС;
* серцева недостатність;
* фібриляція передсердь.

## 2. Що доцільно залишити у Free

Free має залишатися достатньо корисним, щоб лікар міг реально оцінити продукт і регулярно ним користуватися.

Доцільно залишити безкоштовними:

* доступ до головної сторінки;
* базову форму «Асистент лікаря» без серверного збереження;
* базові калькулятори високого попиту: SCORE2, ШКФ, ІМТ, CHA2DS2-VASc / HAS-BLED;
* базові опитувальники: GAD-7, PHQ-9, FINDRISC;
* перегляд частини довідника «Препарати»;
* перегляд частини шаблонів «Хвороби»;
* SEO-сторінки `/egfr`, `/score2`, `/gad7`, `/phq9`, `/findrisk`;
* медичні дисклеймери, FAQ і базові пояснення;
* локальні розрахунки без збереження історії.

Логіка Free: лікар має побачити, що продукт економить час, але Pro має суттєво покращувати щоденну роботу.

## 3. Що можна включити у Pro

Pro варто будувати навколо економії часу, копіювання готових текстів, персональних налаштувань і розширених довідників, а не навколо блокування базових медичних знань.

Потенційні Pro-функції:

* розширені шаблони заключень;
* розширені шаблони рекомендацій;
* конструктор власних шаблонів лікаря;
* збереження власних фраз і стандартних блоків;
* розширені УЗД-протоколи;
* повний ЕКГ-помічник;
* розширені клінічні алгоритми;
* повний довідник препаратів;
* розширений пошук по препаратах;
* швидке копіювання результатів у різних форматах;
* експорт у друкований документ;
* локальне збереження чернеток на пристрої;
* синхронізація особистих налаштувань між пристроями без зберігання медичних даних пацієнтів;
* професійні налаштування: цілі ЛПНЩ, одиниці вимірювання, улюблені модулі, порядок вкладок;
* відключення частини візуальних нагадувань або компактний режим для досвідчених користувачів.

Що не варто робити платним на старті:

* базові шкали ризику;
* базову ШКФ;
* базові опитувальники;
* медичні дисклеймери;
* інформацію, потрібну для безпечного використання інструменту.

## 4. Що потрібно для реєстрації користувачів

Для реєстрації потрібен окремий етап архітектури, бо зараз продукт працює як відкритий локальний інструмент.

Мінімально потрібні зміни:

* обрати провайдера авторизації;
* створити сторінку `/login`;
* створити сторінку `/profile`;
* додати сесію користувача;
* додати кнопку входу або маленький елемент акаунта в інтерфейсі;
* створити серверний шар для перевірки користувача;
* визначити, які дані акаунта зберігаються;
* не зберігати персональні дані пацієнтів у профілі користувача;
* додати політику приватності та умови користування;
* додати механізм виходу з акаунта;
* додати обробку помилок входу.

Рекомендований підхід для MVP:

* email magic link або OAuth через Google;
* мінімальний профіль: email, ім'я або назва лікаря за бажанням, дата створення акаунта;
* без паролів на власному сервері, якщо можна використати готовий auth-провайдер;
* без збереження пацієнтів на сервері.

## 5. Що потрібно для зберігання статусу підписки

Статус підписки не варто зберігати тільки у браузері, бо користувач може змінити localStorage.

Потрібен серверний або керований backend-шар, який зберігає:

* userId;
* email;
* plan: `free` або `pro`;
* subscriptionStatus: `active`, `trialing`, `past_due`, `canceled`, `expired`;
* paymentProviderCustomerId;
* paymentProviderSubscriptionId;
* currentPeriodEnd;
* createdAt;
* updatedAt.

Потрібна синхронізація з платіжною системою:

* webhook після успішної оплати;
* webhook після скасування;
* webhook після невдалої оплати;
* webhook після завершення пробного періоду;
* захист webhook endpoint від підробки.

У браузері можна тримати тільки короткий стан для UI:

* користувач увійшов чи ні;
* план Free / Pro;
* які кнопки показувати.

Остаточне рішення про доступ до Pro має перевірятися на сервері.

## 6. Які сторінки потрібно додати

### `/pricing`

Сторінка тарифів:

* Free;
* Pro;
* коротке порівняння;
* що залишається безкоштовним;
* що входить у Pro;
* дисклеймер, що продукт не замінює клінічне рішення.

### `/login`

Сторінка входу:

* email magic link або OAuth;
* коротке пояснення, що акаунт потрібен для Pro-функцій і налаштувань;
* посилання на privacy / terms.

### `/profile`

Особистий профіль лікаря:

* email;
* тариф;
* статус підписки;
* дата наступного списання або завершення доступу;
* кнопка керування підпискою;
* налаштування продукту;
* вихід з акаунта.

Не зберігати тут персональні дані пацієнтів.

### `/privacy`

Політика приватності:

* які дані збираються;
* які дані не збираються;
* Google Analytics;
* cookies або локальне збереження;
* авторизація;
* оплата;
* контакт для питань.

Окремо вказати: продукт не повинен зберігати персональні медичні дані пацієнтів без окремого рішення.

### `/terms`

Умови користування:

* продукт є допоміжним інструментом для лікаря;
* лікар приймає остаточне клінічне рішення;
* обмеження відповідальності;
* правила використання;
* заборона використання як сервісу самодіагностики пацієнтів;
* умови Pro-доступу.

### `/refund`

Політика повернення коштів:

* коли можливе повернення;
* за який період;
* як звернутися;
* що відбувається після скасування підписки.

Фінальні формулювання потрібно узгодити юридично перед запуском оплати.

## 7. Де потрібно перевіряти доступ Pro

Перевірка Pro має бути в тих місцях, де функція дає додаткову економію часу або розширений професійний сценарій.

Потенційні точки перевірки:

* розширені шаблони у вкладці «Асистент лікаря»;
* збереження власних шаблонів;
* експорт документів;
* розширені УЗД-протоколи;
* розширені ЕКГ-підрозділи;
* повний довідник препаратів;
* розширені картки хвороб;
* генератор рекомендацій;
* персональні налаштування;
* синхронізація між пристроями.

Технічно бажано мати єдину функцію або компонент:

* `isProUser`;
* `RequirePro`;
* `ProBadge`;
* `UpgradePrompt`.

Важливо: не розкидати перевірки доступу вручну по всьому коду без єдиної логіки, інакше потім буде важко підтримувати продукт.

## 8. Технічні та безпекові ризики

### Медичні дані

Найбільший ризик — випадково почати зберігати персональні дані пацієнтів.

Щоб уникнути цього:

* не зберігати пацієнтів на сервері;
* не зберігати тексти заключень у backend;
* не відправляти введені клінічні дані у сторонні сервіси;
* залишити клінічні форми локальними;
* якщо збереження буде потрібне, спочатку проєктувати окрему модель безпеки.

### Авторизація

Ризики:

* слабкі паролі, якщо робити власну систему;
* викрадення сесії;
* неправильна робота logout;
* відкриття Pro-функцій без перевірки на сервері.

Рекомендація: не робити власну auth-систему з паролями на старті.

### Оплата

Ризики:

* неправильне оновлення статусу підписки;
* доступ Pro після скасування;
* відсутність webhook-перевірки;
* різниця між статусом у браузері та статусом у платіжній системі.

Рекомендація: статус підписки має оновлюватися через webhook і перевірятися на сервері.

### Frontend-only обмеження

Якщо Pro-доступ перевіряти тільки в React або localStorage, це легко обійти.

Frontend може приховувати кнопки, але не повинен бути єдиним джерелом правди для платного доступу.

### Юридичні ризики

Потрібні:

* privacy policy;
* terms of use;
* refund policy;
* чіткі медичні дисклеймери;
* пояснення, що продукт не є медичною інформаційною системою для зберігання карт пацієнтів, якщо така функція не реалізована.

### UX-ризики

Монетизація може зіпсувати продукт, якщо:

* заблокувати забагато базових функцій;
* зробити агресивні paywall-вікна;
* вимагати реєстрацію до того, як лікар зрозумів користь;
* додати багато маркетингового шуму.

Рекомендація: м'який paywall тільки на розширені професійні сценарії.

## 9. Поетапний план реалізації без зберігання персональних даних пацієнтів

### Етап 0. Підготовка

Мета: нічого не ламати й не впроваджувати оплату передчасно.

Дії:

* визначити Free / Pro межі;
* створити `/pricing`, `/privacy`, `/terms`, `/refund` як інформаційні сторінки;
* не додавати реєстрацію;
* не додавати оплату;
* не додавати базу даних.

Результат: сайт готовий пояснювати майбутню модель, але залишається відкритим.

### Етап 1. М'який Pro-шар без платежів

Мета: перевірити, які функції реально мають цінність.

Дії:

* додати в інтерфейс позначки `Pro незабаром`;
* не блокувати критичні базові інструменти;
* збирати фідбек від лікарів;
* через Google Analytics дивитися, які модулі використовують найчастіше.

Результат: зрозуміло, за що потенційно готові платити.

### Етап 2. Авторизація без медичних даних

Мета: дати лікарю акаунт для доступу до Pro і налаштувань.

Дії:

* додати `/login`;
* додати `/profile`;
* обрати auth-провайдера;
* зберігати тільки дані акаунта, а не дані пацієнтів;
* додати session handling;
* додати серверну перевірку користувача.

Результат: користувач може увійти, але клінічні дані залишаються локальними.

### Етап 3. Підписка

Мета: підключити оплату без зміни клінічної логіки.

Дії:

* обрати платіжного провайдера;
* створити checkout;
* створити customer portal;
* додати webhook;
* зберігати статус підписки;
* перевіряти Pro-доступ на сервері.

Результат: Pro-доступ працює, але пацієнтські дані не передаються на сервер.

### Етап 4. Pro-функції

Мета: додати функції, які реально економлять час.

Перші кандидати:

* власні шаблони лікаря;
* розширені рекомендації;
* компактний професійний режим;
* експорт документів;
* розширені УЗД / ЕКГ модулі;
* повний довідник препаратів.

Результат: платний тариф має практичну цінність, а Free залишається корисним.

### Етап 5. Обережна синхронізація налаштувань

Мета: зробити продукт зручнішим між пристроями без зберігання пацієнтів.

Можна синхронізувати:

* улюблені модулі;
* порядок вкладок;
* власні шаблонні фрази;
* одиниці вимірювання;
* налаштування інтерфейсу.

Не синхронізувати без окремого рішення:

* ПІБ пацієнта;
* діагнози конкретних пацієнтів;
* заключення;
* результати конкретних консультацій;
* медичні документи пацієнта.

## Рекомендована стратегія

Не починати з оплати.

Спочатку варто:

1. Додати сторінку `/pricing` як пояснення майбутньої моделі.
2. Визначити, які функції будуть Pro.
3. Подивитися через аналітику, які модулі реально використовують.
4. Зібрати фідбек від лікарів.
5. Лише після цього додавати авторизацію і підписку.

Найкраща перша Pro-цінність для «Асистента лікаря» — не доступ до калькуляторів, а економія часу: власні шаблони, розширені протоколи, копіювання, експорт, персональні налаштування і професійні довідники.
